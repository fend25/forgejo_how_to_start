# Как поднять и настроить свой Git - Forgejo

## Основная идея

Создать себе "свой гитхаб" - своё гит-хранилище и private docker registry. Также за компанию сюда прилетает wiki, система управления проектами (kanban) и быстрый интерфейс. Важным требованием является то, что вся эта красота будет доступна только изнутри VPN (wireguard в данном случае), с кастомным доменом и с полной и качественной поддержкой SSL - с замочком в браузере. То есть https://git.mytld, и никаких хвостов типа порта ":9443" в ссылке или "продолжить с небезопасным SSL". И с красивым доступом по SSH без мишуры ":2222" в git+ssh ссылках репозиториев.

## Требования и предполагаемая подготовка сервера

1. VPS на Ubuntu LTS (проверено на Ubuntu 24.04 LTS)

2. SSH убран с 22 порта куда-нибудь на порт повыше:)

3. Настроен wireguard

4. Настроен dnsmasq с доменом git.mytld

5. Настроен веб-сервер (например caddy) который умеет обрабатывать ssl для доменов git.mytld

6. Root CA сертификат от зоны .mytld уже добавлен в сертификаты хост-системы (то есть он присутствует в `/etc/ssl/certs/ca-certificates.crt` )

7. Настроен отдельный пользователь без sudo, у пользователя настроен rootless docker и включен linger. В данном примере у пользователя UID 1005 и GID 1005

## Этапы установки

### 1. Файлы

На целевой машине создаем папку где будет размещаться форгежо (обычно это `$HOME/apps/forgejo`  или просто `$HOME/forgejo`) файлы. Переходим в эту папку и создаем в ней папку `runner_data_1`. После чего копируем файлы:

1. docker-compose.yml

2. runner_data_1/config.yml

### 2. Compose

Правим Compose под целевое использование - проверяем номера версий, правим везде uid/gid под целевой.

Compose файл содержит три проекта:

1. **forgejo** — Git-хостинг, веб-интерфейс, API, container registry и wiki. Принимает пуши, управляет репозиториями, хранит пакеты и раздаёт задания раннерам через Actions API.

2. **forgejo_docker** — docker in docker (DinD). Предоставляет Docker-сервис, в котором запускаются CI-джобы. Runner не выполняет задачи сам — он просит forgejo_docker создать эфемерный контейнер для каждой джобы, выполнить в нём шаги workflow, и уничтожить после завершения. Также через него выполняются `docker build` и `docker push` из CI-пайплайнов.

3. **forgejo_runner_1** — CI-раннер. Получает задания от Forgejo, просит DinD создать эфемерный контейнер и выполнить в нём шаги workflow. Сам ничего не билдит — только оркестрирует. Для параллельного выполнения джоб можно добавить дополнительные раннеры (forgejo_runner_2, forgejo_runner_3...), каждый может выполнять только одну джобу в один момент времени.

Важные моменты:

1. Forgejo мы используем именно root версию (не rootless), и проставляем ей env vars USER_UID и USER_GID. Таким образом forgejo запустится как ему надо, спокойно заберет себе 22 порт ssh (это будет важно позднее) и переключится на указанный uid

2. Проверяем что во всех трех контейнерах проброшены в RO-режиме вольюмы с `/etc/ssl/certs/ca-certificates.crt` и /etc/localtime с /etc/timezone. Первый нужен для того чтобы потом сборщики у раннера спокойно ходили в registry с корректным SSL, а время - чтобы корректно отображалось время в сборщиках, а не в UTC.

3. В нашем конфиге раннера `./runner_data_1/config.yml` предполагаются авто-проброшенные вольюмы и опции. Это позволит нам писать джобы без лишнего визуального мусора в yaml файлах в репозиториях. Если это дает слишком широкие доступы, можно подправить список вольюмов на свой вкус.
   
   1.   valid_volumes:
          - '/var/run/docker.sock'
          - '/etc/ssl/certs/ca-certificates.crt'
          - '/etc/timezone'
          - '/etc/localtime'
   
   2. options: '-v /etc/ssl/certs/ca-certificates.crt:/etc/ssl/certs/ca-certificates.crt:ro -v /var/run/docker.sock:/var/run/docker.sock -v /etc/timezone:/etc/timezone:ro -v /etc/localtime:/etc/localtime:ro'

### 3. Первоначальная настройка

Настраиваем реверс-прокси на порт на котором планируем что будет слушать forgejo, запускаем докер - `docker compose up -d` и идем в браузер проверять, что по адресу git.mytld форгежо работает. Он по традиции должен встретить нас начальным экраном с выбором базовых настроек. Настраиваем, сохраняем свой пароль, мы великолепны! Время идти и настраивать раннер.

После этого идем в https://git.mytld.user/settings/keys и добавляем свой публичный ssh ключ, чтобы все по красоте заработало по ssh, и gpg - если захотим.

Также необходимо включить Actions в конфигурации Forgejo. Для этого проверяем что в секции `[actions]` ENABLED=true или добавляем всю секцию в `./forgejo/gitea/conf/app.ini`:

```ini
[actions]
ENABLED = true
```

После внесения изменений в app.ini нужно перезапустить контейнер forgejo: `docker compose restart forgejo`

### 4. Бесшовная работа ssh

SSH хочется иметь на 22 порту для красивых ссылок на репозитории без торчащих в середине портов. В целом этот пункт не обязательный, но с ним будет приятнее работать.

Но в чем проблема: мы запускаем forgejo в rootless docker и на sudoless пользователе, 22й порт не открыть. Мы сделаем буквально workaround: средствами линукса мы будем форвардить трафик с 22 порта на другой порт (в нашем примере это 2222), а в композе пропишем для forgejo обратный маппинг: "2222:22". Таким образом для внешнего наблюдателя это будет 22 порт, изнутри форгежо также будет работать через 22 порт, а в промежутке между внешним пользователем и форгежо будет "петля", которая будет вести трафик через 2222 порт, позволяя таким образом не поднимать права пользователя и оставаться в sudoless окружении.

Поскольку у нас уже есть wireguard на сервере и мы хотим чтобы 22 порт был открыт только для пользователей из wireguard сети, то разумнее всего и "прицепиться" к wireguard конфигу. К тому же, если мы пойдем настраивать правила непосредственно в iptables/nftables/ufw, то эти правила применятся при старте системы (рано или поздно машину кто-нибудь ребутнёт), и до того как стартанёт wireguard, а значит до появления сетевого интерфейса wg0. А значит правила просто не применятся, так как эти правила будут применяться системой к несуществующему (на момент "сразу после старта ОС") сетевому интерфейсу. 

*Примечание: если ваш wireguard интерфейс называется не wg0, значит вы уже знаете что мы делаем и справитесь отмапить инструкцию под свой сетап :)*

Итак, дописываем в /etc/wireguard/wg0.conf:

```yaml
PostUp = iptables -t nat -A PREROUTING -i %i -p tcp --dport 22 -j REDIRECT --to-port 2222
PreDown = iptables -t nat -D PREROUTING -i %i -p tcp --dport 22 -j REDIRECT --to-port 2222
```

И рестартуем сервис wg0.

Это сделает как раз то, что нужно - перенаправит входящий трафик порта 22 на порт 2222. И только для интерфейса wg0, не трогая все остальные, так что даже случайно потом открыв порт 2222 в каком-нибудь приложении мы не получим волну сканеров, ломящихся на сервак по 22 порту.

### 5. Регистрация раннера

Так как нам нужен не просто гит от forgejo, а полноценная среда с приватным docker registry и сборщиком проектов, наподобие github pipelines, то нам нужен и runner. 

В compose файле есть два способа запускать раннер. Первый способ - закомментированный на листинге ниже - для того чтобы регистрировать раннер. Второй - чтобы запускать "в обычной жизни".

```yaml
#user: 0:0
#command: '/bin/sh -c "while :; do sleep 1; done"' # "forgejo-runner register" и "chown -R 1005:1005 /data" и "chown 1005:1005 config.yml"
user: 1005:1005
command: '/bin/sh -c "sleep 5; forgejo-runner daemon --config=config.yml"'
```

Как регистрировать runner:

1. Перекомментируем строки, активируя 0:0 и while-do-sleep цикл, и комментируя 1005:1005 и forgejo-runner

2. Перезапускаем раннер: `docker compose restart forgejo_runner_1`

3. Идем в forgejo web ui, Admin Panel -> Actions -> Runners ( https://git.mytld/admin/actions/runners ) и добавляем кнопочку Add Runner. По нажатию нам выдадут токен раннера, сохраняем его себе в блокнотик.

4. Заходим в шелл раннера: `docker exec -it forgejo_runner_1 sh`

5. Выполняем регистрацию раннера: `forgejo-runner register`
   
   1. На каком-то этапе нас спросят токен, вводим токен из forgejo
   
   2. Адрес вводим от форгежо: https://git.mytld
   
   3. Название раннера должно номер, чтобы потом можно было расширяться, можно взять аналогичный названию контейнера - forgejo_runner_1

6. Фиксим права на нужные файлики:
   
   1. `chown -R 1005:1005 /data`
   
   2. `chown 1005:1005 config.yml`

7. Выходим из контейнера

8. Обратно меняем в композе комментирование строк - комментируя 0:0 и while-do-sleep цикл, и активируя 1005:1005 и forgejo-runner

9. Перезапускаем раннер: `docker compose restart forgejo_runner_1`

10. Идем в форгежо https://git.mytld/admin/actions/runners и проверяем что раннер есть и он зеленый, должен быть статус "простаивает".

В дальнейшем, чтобы добавить еще раннер, нужно создать папку forgejo_runner_2, скопировать в неё config.yml, добавить в compose файл еще один контейнер forgejo_runner_2, и аналогичным образом зарегистрировать новый раннер.

## Создание пользователя для пуша в registry

Дело в том, что на февраль 2026 года forgejo [так и не научился](https://codeberg.org/forgejo/forgejo/issues/3571) разрешать пуш в registry через автоматически создаваемый токен экшена:
`docker login git.mytld -u ${{ github.actor }} -p ${{ secrets.GITHUB_TOKEN }}` 

Вот гитхаб так умеет, а forgejo - пока что нет.

Поэтому придется несколько повозиться. Общий план такой:

1. Создаем дополнительного юзера, можно назвать его bot или builder.

2. Создаем этому пользователю (придется под ним залогиниться) access токен с правами только на чтение и запись в registry.

3. В организации репозитория создаем команду, с правами только на registry, снова на read-write.

4. В эту команду добавляем бота.

5. В настройках репозитория добавляем переменную с логином бота и секрет с токеном бота.

Таким образом мы сможем в джобе логиниться в registry через такую команду:

`echo "${{ secrets.REGISTRY_TOKEN }}" | docker login git.mytld -u ${{ vars.REGISTRY_USER }} --password-stdin`

Всё, мы великолепны!

В целом этому же боту можно создать еще один токен, только на read registry и этим токеном логиниться на продакшн тачке чтобы пуллить image продакшн-сборки.
